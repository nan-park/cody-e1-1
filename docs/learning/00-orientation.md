# 0단계 · 오리엔테이션 — 이 미션이 푸는 문제

## 배운 개념

### 이 미션의 한 줄 요약

> **"내 컴퓨터에서만 되는데요?"를 없애는 작업.**

프로그램은 혼자 돌아가지 않는다. 특정 버전의 언어, 라이브러리, 설정이 맞아야 실행된다.
그래서 내 노트북에서 잘 돌던 코드가 팀원 노트북·서버에서는 안 돌아간다.
이 미션은 그 문제를 **실행 환경을 통째로 포장해서 넘기는 방식**으로 푸는 연습이다.

### 도구 3개의 역할 분담

| 도구 | 한 줄 정의 | 비유 |
|---|---|---|
| **터미널(CLI)** | 마우스 대신 글자로 컴퓨터에 명령하는 창 | 서랍을 직접 여는 대신 "3번 서랍 열어"라고 말하기 |
| **Docker** | 프로그램 + 실행에 필요한 모든 것을 상자에 담아 어디서든 똑같이 실행 | 이삿짐 컨테이너(규격만 맞으면 배·트럭 상관없음) |
| **Git / GitHub** | 변경 이력을 저장(Git)하고 인터넷에 올려 공유(GitHub) | Git = 저장 + 되돌리기, GitHub = 그 기록을 올려두는 클라우드 |

### 먼저 잡고 가야 할 Docker 용어 2개

- **이미지(Image)** = 붕어빵 **틀**. 실행되지 않는 정지된 패키지.
- **컨테이너(Container)** = 그 틀로 찍어낸 **붕어빵**. 실제로 돌아가는 프로그램.

> **이미지 1개 → 컨테이너 N개.**
> 틀 하나로 붕어빵 100개를 똑같이 찍을 수 있다는 것,
> 이게 "재현 가능한 환경"의 정체다.

## 헷갈리기 쉬운 지점

- **"Docker를 설치한다 = 프로그램이 빨라진다"가 아니다.** Docker가 푸는 건 성능 문제가 아니라 **환경 불일치 문제**다.
- **이미지와 컨테이너를 같은 말로 쓰지 않기.** 이미지는 파일(정지), 컨테이너는 프로세스(실행 중). 4단계에서 `docker images`와 `docker ps`가 따로 있는 이유가 이것이다.

## 전체 로드맵

```
1단계  터미널 기본기      폴더 만들고, 옮기고, 지우기 + 절대경로/상대경로
2단계  파일 권한          755, 644가 무슨 뜻인지 직접 실험으로 확인
3단계  Docker 점검        설치 확인 + 엔진이 살아있는지 확인
4단계  컨테이너 실행      hello-world, ubuntu 안에 직접 들어가 보기
5단계  나만의 이미지      Dockerfile 직접 작성 → 웹 서버 이미지 빌드
6단계  포트 매핑          브라우저로 내 컨테이너에 접속
7단계  마운트 & 볼륨      파일 실시간 반영 / 컨테이너 지워도 데이터 남기기
8단계  Git & GitHub       기록 남기고 원격 저장소에 제출
```

## 한 줄 정리

> 개발 환경 세팅은 "코드를 짜기 전 준비 운동"이 아니라, **코드가 어디서든 같은 방식으로 돌아가게 만드는 작업 그 자체**다.
