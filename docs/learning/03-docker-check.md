## 배운 개념

### Docker가 푸는 문제

```
나:   macOS + Python 3.12 + 라이브러리 A 1.2  → 잘 돌아감
동료: Windows + Python 3.9  + 라이브러리 A 2.0 → 에러
서버: Ubuntu  + Python 3.11 + 라이브러리 A 없음 → 에러
```

해결책은 두 갈래였다.

| | 가상머신(VM) | 컨테이너(Docker) |
|---|---|---|
| 방식 | 가짜 컴퓨터를 통째로 하나 더 | OS는 호스트 것을 **빌려 쓰고** 프로그램만 격리 |
| 무게 | OS 전체 복사 → 수십 GB | 수십 MB |
| 시작 | 수십 초~1분 | 1초 |

```
     가상머신(VM)                        컨테이너(Docker)

┌──────┬──────┬──────┐            ┌──────┬──────┬──────┐
│ 앱A  │ 앱B  │ 앱C  │            │ 앱A  │ 앱B  │ 앱C  │
├──────┼──────┼──────┤            ├──────┴──────┴──────┤
│ OS   │ OS   │ OS   │ ← 무거움    │   Docker 엔진      │ ← 가벼움
├──────┴──────┴──────┤            ├────────────────────┤
│    가상화 소프트웨어  │            │   호스트 OS 커널     │ ← 공유
├────────────────────┤            ├────────────────────┤
│     호스트 OS       │            │      하드웨어       │
└────────────────────┘            └────────────────────┘
```

아파트 비유: VM은 집집마다 **발전소와 상수도를 따로 짓는 것**,
컨테이너는 전기·수도를 공유하되 **현관문으로만 분리**된 것.

### 용어 4개

| 용어 | 뜻 | 비유 |
|---|---|---|
| **이미지** | 실행에 필요한 모든 것이 담긴 정지된 패키지 | 붕어빵 틀 |
| **컨테이너** | 이미지를 실행한 상태 | 찍어낸 붕어빵 |
| **레지스트리** | 이미지를 모아둔 인터넷 창고(Docker Hub) | 앱스토어 |
| **데몬** | 뒤에서 계속 돌며 실제 일을 하는 프로그램 | 주방장 |

### Docker의 구조 — 왜 점검이 2단계인가

```
   내가 치는 명령            실제로 일하는 쪽              인터넷
┌──────────────┐        ┌────────────────────┐      ┌──────────────┐
│ docker CLI   │ ─요청→ │   Docker 데몬        │ ─→   │  Docker Hub  │
│  (클라이언트) │ ←응답─ │  (엔진, 백그라운드)   │      │  (레지스트리) │
└──────────────┘        └────────────────────┘      └──────────────┘
     주문서                     주방장                     식자재 창고
```

- `docker --version` → **주문서(CLI)가 설치돼 있나?**
- `docker info` → **주방장(데몬)이 실제로 출근해 있나?**

> **버전 출력은 데몬 없이도 나온다.** 그래서 `--version`만으로는 점검이 부족하고
> `docker info`의 **`Server:` 섹션이 응답하는지**까지 봐야 한다.

데몬이 꺼져 있으면:

```
Server:
ERROR: Cannot connect to the Docker daemon at unix:///... Is the docker daemon running?
```

### 실제 점검 결과 (이 환경)

| 항목 | 값 |
|---|---|
| Docker CLI | 28.5.2 |
| Docker Compose | v2.40.3 |
| 데몬 응답 | 정상 (`Server:` 섹션 출력됨) |
| Context | `orbstack` |
| 이미지 / 컨테이너 | 0개 / 0개 (백지 상태) |
| Storage Driver | overlay2 (이미지를 **층layer**으로 쌓아 저장 — 5단계에서 재등장) |

### OrbStack이라는 우회로

```
$ docker context ls
NAME         DOCKER ENDPOINT
default      unix:///var/run/docker.sock                              ← 시스템 영역 (sudo 필요)
orbstack *   unix:///Users/nika.dev02147536/.orbstack/run/docker.sock ← 내 홈 폴더 (sudo 불필요)
```

`*` 가 현재 사용 중인 연결 대상. 원래 Docker는 `/var/run/docker.sock`이라는 **시스템 영역**의 통로를 쓰는데, 거기에 설치하려면 관리자 권한이 필요하다. OrbStack은 통로를 **내 홈 폴더 안**으로 옮겨 `sudo` 없이 동작하게 만든다. (서울캠퍼스 sudo 제한을 우회하는 방법)

> `.sock` = **소켓**. CLI와 데몬이 대화하는 창구 역할의 특수 파일.

### macOS인데 리눅스 컨테이너가 왜 돌아가나

컨테이너는 "호스트 커널을 공유"하는데 **macOS에는 리눅스 커널이 없다.** 힌트는 출력에 있었다.

```
Server Version: 28.5.2 / OS: OrbStack / Arch: x86_64 / CPUs: 6
                         ↑ macOS가 아님
```

```
macOS (내 맥북)
 └─ OrbStack이 띄운 초경량 리눅스 VM
     └─ Docker 데몬
         └─ 컨테이너들   ← 여기서 리눅스 커널을 공유
```

> macOS/Windows의 Docker는 "VM이 없다"가 아니라 **"VM 하나를 모두가 공유한다"** 가 정확하다.
> 리눅스 서버에서는 이 중간 VM이 아예 없다.

## 헷갈리기 쉬운 지점

### 1. `WARNING`은 에러가 아니다

```
WARNING: DOCKER_INSECURE_NO_IPTABLES_RAW is set
```

OrbStack이 자체 네트워크 방식을 쓰느라 리눅스 방화벽 기능 일부를 끄면서 알려주는 **안내**다. 실습에 영향 없음.

### 2. `docker --version`이 되면 Docker가 정상이다? → 아니다

CLI만 깔려 있고 데몬이 안 떠 있으면 명령은 쳐지는데 아무 일도 안 일어난다.
초보자가 가장 많이 겪는 `Cannot connect to the Docker daemon`이 이 상황.

## 내가 던진 질문들

### Q. 리눅스 서버에서 macOS/Windows 도커를 만들려면 중간 VM이 필요한 거야?

**그 방향으로는 아예 안 된다.** 대칭이 아니다.

이유는 컨테이너의 원리 때문:

```
컨테이너 = 프로그램 + 라이브러리        (커널 없음, 호스트 것을 빌림)
VM       = 프로그램 + 라이브러리 + 커널  (전부 자기 것)
```

리눅스 컨테이너 속 프로그램은 리눅스 커널에게 시스템 콜을 보내는데, 윈도우 프로그램은 **완전히 다른 언어로** 요청한다. 리눅스 커널은 못 알아듣는다.
즉 **컨테이너는 호스트와 같은 종류의 커널을 요구한다.**

| 호스트 | 리눅스 컨테이너 | 윈도우 컨테이너 | macOS 컨테이너 |
|---|---|---|---|
| **리눅스** | ✅ 그대로 (VM 불필요) | ❌ 불가 | ❌ 불가 |
| **macOS** | ✅ 리눅스 VM 경유 | ❌ 불가 | ❌ 존재 안 함 |
| **윈도우** | ✅ 리눅스 VM 경유 | ✅ 그대로 | ❌ 불가 |

- **윈도우 컨테이너**: 존재하지만 **윈도우 커널이 필요해 윈도우 호스트에서만** 돌아간다. 리눅스 위에 윈도우 VM을 올리는 순간 그건 이미 컨테이너가 아니라 그냥 가상머신이고, 가벼움이라는 장점이 전부 사라진다.
- **macOS 컨테이너**: 존재하지 않는다. ① 기술적으로 macOS 커널에 컨테이너 기능(리눅스의 namespace/cgroup에 해당)이 없고, ② 법적으로 Apple 라이선스가 **Apple 하드웨어에서만** 실행하도록 제한한다. (iOS 앱 빌드 CI가 클라우드에서도 실제 Mac 하드웨어를 쓰는 이유)

> **세로로 읽으면 결론이 보인다: 리눅스 컨테이너만 어디서나 돌아간다.**
> 그래서 "Docker 이미지"는 사실상 전부 리눅스 이미지다(nginx, python, node, ubuntu 모두).
> 개발자가 맥을 쓰든 윈도우를 쓰든 **모두 같은 리눅스 환경에서 개발하게 되는** 효과가 생기고,
> 이게 "내 컴퓨터에서만 돌아가는 문제"를 없애는 실질적 원리다.

### Q. CPU 종류가 다르면 어떤 일이 생겨?

**직접 실험한 결과** (이 맥은 인텔 x86_64):

```
$ uname -m                                                  → x86_64
$ docker run --rm alpine uname -m                           → x86_64   (알아서 맞는 걸 받음)
$ docker run --rm --platform linux/arm64 alpine uname -m    → aarch64  (ARM용이 실행됨!)
```

경우가 셋으로 갈린다.

**① 멀티 아키텍처 이미지 → 아무 일도 안 일어남**
`alpine` 같은 주요 공식 이미지는 하나의 이름 아래 여러 CPU용 버전을 갖고 있어 Docker가 알아서 고른다. 평소 이걸 의식 못 하는 이유.

**② 강제 실행 → 에뮬레이션 (돌아가지만 느림)**
QEMU라는 번역기가 명령어를 실시간 통역한다. **2~10배 느려진다.** 빌드 작업을 이 상태로 돌리면 몇 분이 수십 분이 된다.

**③ 번역기 없음 → 에러**

```
exec /bin/sh: exec format error
```

> **`exec format error` = "CPU 종류가 안 맞다"** 로 외워둘 것.
> 원인을 짐작하기 어려운 대표적 에러다.

**실무에서 터지는 시나리오**:

```
M칩 맥북에서 빌드 (arm64) → Docker Hub push → 인텔 서버에서 pull → exec format error 💥
```

해결: `docker build --platform linux/amd64 -t my-web:1.0 .`
또는 `docker buildx`로 양쪽 버전을 한 번에 빌드.

### Q. 64와 32의 차이가 뭐야?

먼저 **두 축을 분리**해야 한다. 이게 핵심.

```
축 1) 명령어 체계(설계 가문) :  x86 계열   vs   ARM 계열
축 2) 비트 수               :  32비트     vs   64비트
```

| 이름 | 가문 | 비트 | 어디에 |
|---|---|---|---|
| `x86` (i386) | x86 | 32 | 옛날 PC |
| `x86_64` / `amd64` | x86 | **64** | 이 맥, 대부분의 서버 |
| `armv7` | ARM | 32 | 구형 라즈베리파이, 옛 스마트폰 |
| `arm64` / `aarch64` | ARM | **64** | M칩 맥, 아이폰, 최신 서버 |

**비트 수** = CPU가 한 번에 처리하는 데이터 덩어리 크기(삽의 크기).
실질적으로 더 중요한 건 **주소를 몇 자리까지 셀 수 있느냐**다.

```
32비트: 2³² = 약 42억 개 주소 → 최대 약 4GB 메모리
64비트: 2⁶⁴ = 약 1800경 개    → 사실상 무제한
```

> "32비트 컴퓨터는 램 4GB를 못 넘는다"는 말이 여기서 나온다.
> 램을 8GB 꽂아도 주소를 못 세니 4GB만 인식한다.
> (우편번호가 5자리면 주소를 10만 개까지밖에 못 만드는 것과 같다)

**지금 실무에서 마주치는 갈등은 비트 수가 아니라 가문 차이**(`amd64 ↔ arm64`)다.
64비트가 기본이 된 지 오래고, Docker Hub 주요 이미지도 32비트 지원을 대부분 중단했다.

**정리하면**:
- **OS 종류가 다르다** → 넘을 수 없는 벽 (VM을 새로 띄우는 수밖에)
- **CPU 종류가 다르다** → 느리지만 에뮬레이션으로 통과 가능
