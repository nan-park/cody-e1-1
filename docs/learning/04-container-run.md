# 4단계 · 컨테이너 실행과 운영

> 실습 로그: [`docs/logs/04-container-run.log`](../logs/04-container-run.log)

## 배운 개념

### `docker run`은 사실 3가지를 한다

```
docker run hello-world
        ├─ ① pull    : 이미지가 없으면 Docker Hub에서 내려받고
        ├─ ② create  : 그 이미지로 컨테이너를 만들고
        └─ ③ start   : 컨테이너를 실행한다
```

이미지 0개 상태에서 실행하니 3단계가 그대로 출력됐다.

```
Unable to find image 'hello-world:latest' locally     ← ① 로컬에 없네?
latest: Pulling from library/hello-world              ← ② 받는다
Hello from Docker!                                    ← ③ 실행 결과
```

> **"로컬에 없으면 알아서 받아온다"는 편리함이자 함정.**
> 이름만 보고 인터넷에서 받아 실행하는 셈이므로 신뢰할 수 있는 이미지인지 확인하는 습관이 필요하다.
> (공식 이미지는 `library/`로 시작)

### 명령어 구조 — 이미지 이름이 경계선

```
docker run  -it  --name ubuntu-lab  ubuntu:24.04  bash
            └── Docker 옵션 ──────┘  └─ 이미지 ─┘  └ 컨테이너 안에서 실행할 명령 ┘
```

| 조각 | 의미 |
|---|---|
| `-i` | **i**nteractive — 내 키보드 입력을 컨테이너로 전달 |
| `-t` | **t**ty — 가상 터미널을 붙여줌(프롬프트가 보이는 이유) |
| `--name` | 컨테이너 이름표. 없으면 `angry_johnson` 같은 무작위 이름 |
| `ubuntu:24.04` | 이미지**:**태그. 생략하면 `:latest` |
| `bash` | **이게 PID 1이 된다** |

```sh
docker run -it ubuntu:24.04 bash   # ⭕
docker run ubuntu:24.04 -it bash   # ❌ "-it"를 컨테이너 안에서 실행하려 함 → 에러
```

### `-it` vs `-d`

| 옵션 | 뜻 | 동작 |
|---|---|---|
| `-it` | interactive + tty | 앞에서(foreground) 실행. 내가 나가면 끝 |
| `-d` | **d**etached | 백그라운드로 분리. 터미널과 무관하게 계속 |

`-d`로 띄우면 컨테이너 ID만 출력하고 프롬프트가 바로 돌아온다.
단 **끝나지 않는 명령**을 줘야 유지된다(`sleep infinity`). 실제 서비스에서는 이 자리에 `nginx` 같은 서버 프로세스가 들어간다.

### 이미지 ≠ 컨테이너 (명령이 따로 있는 이유)

| 명령 | 보여주는 것 | 비유 |
|---|---|---|
| `docker images` | 이미지(정지된 패키지) | 붕어빵 **틀** 재고 |
| `docker ps` | **실행 중인** 컨테이너 | 지금 굽고 있는 붕어빵 |
| `docker ps -a` | **모든** 컨테이너(종료된 것 포함) | 구운 것 + 식은 것 전부 |

- `docker ps`에 안 보인다고 실행이 실패한 게 아니다. 끝난 컨테이너는 `-a`를 붙여야 보인다.
- 종료된 컨테이너는 **사라지지 않고 `Exited` 상태로 디스크에 남는다.** 쌓이면 청소 필요.
- `Exited (0)`의 `0`은 종료 코드. `0`=정상, 그 외=비정상.

### ⭐ exec vs attach — PID 1이 누구냐의 문제

```
$ docker exec -it ubuntu-daemon bash        $ docker attach ubuntu-attach
root@...:/# ps -ef                          root@...:/# ps -ef | cat
PID  PPID  CMD                              PID  PPID  CMD
  1     0  sleep infinity   ← 메인은 그대로    1     0  bash   ← 내가 붙은 게 PID 1!
 16     0  bash             ← 나는 별개         9     1  ps -ef

exit → 컨테이너 Up 유지 ✅                   exit → 컨테이너 Exited ❌
```

| | `docker exec` | `docker attach` |
|---|---|---|
| 하는 일 | 새 프로세스 **추가** | 메인 프로세스에 **연결** |
| 나갈 때 | 컨테이너 **유지** | 컨테이너 **종료** |
| 동시 접속 | 여러 개 가능 | PID 1은 하나뿐 |
| 용도 | 디버깅, 파일 확인 | 메인 프로세스 출력 직접 보기 |

> 병원 비유: `exec`은 **면회객**, `attach`는 **환자 본인의 의식**.
> 면회객이 나가도 환자는 그대로지만, 환자가 나가면 병실이 빈다.

**실무에서는 거의 항상 `exec`.** `attach`는 실수로 서비스를 내리기 쉽다.
(`attach`에서 컨테이너를 살린 채 빠져나오려면 `exit` 대신 `Ctrl+P`, `Ctrl+Q`)

### 운영 명령

| 명령 | 하는 일 | 메모 |
|---|---|---|
| `docker logs` | 메인 프로세스가 **화면에 출력한 내용** | 컨테이너엔 터미널이 없어 이게 유일한 창구 |
| `docker stats --no-stream` | CPU/메모리/PIDS | 우분투 컨테이너 1개 = 메모리 **900KB**, PIDS 1 |
| `docker stop` | 정지(상태 보존) | SIGTERM → 10초 후 SIGKILL |
| `docker start` | 정지된 것 재시작 | 같은 컨테이너가 되살아남 |
| `docker rm` / `rm -f` | 삭제 / 실행 중이어도 강제 삭제 | 되돌릴 수 없음 |
| `docker container prune` | 정지된 컨테이너 일괄 청소 | |
| `docker top` | 컨테이너 프로세스를 **호스트 관점**에서 보기 | 네임스페이스 확인용 |

```
       docker run
           ↓
    ┌─────────────┐   docker stop    ┌──────────┐   docker rm   ┌────────┐
    │  Up (실행중) │ ───────────────→ │  Exited  │ ────────────→ │  삭제됨 │
    │             │ ←─────────────── │  (정지)   │               └────────┘
    └─────────────┘   docker start   └──────────┘
```

**컨테이너를 다 지워도 이미지는 남는다.** 붕어빵을 다 먹어도 틀은 남는 것과 같다.

### 로그는 파일이 아니라 표준 출력으로

`docker logs`가 보여주는 건 **메인 프로세스의 표준 출력**이다. 그래서 Docker의 원칙:

> 컨테이너 안의 프로그램은 로그를 **파일이 아니라 화면(표준 출력)** 에 뿌려야 한다.

파일에 쓰면 컨테이너를 지울 때 같이 사라지고 밖에서 보려면 매번 들어가야 한다.
화면에 뿌리면 Docker가 수집해 주고 중앙 로그 시스템으로도 보낼 수 있다.
(nginx 공식 이미지도 로그 파일을 표준 출력으로 연결해 둠)

## 헷갈리기 쉬운 지점

### 1. `Exited (137)` 은 왜 0이 아닌가

`docker stop`은 먼저 **정중한 종료 요청(SIGTERM)** 을 보내고 10초 기다린 뒤, 안 죽으면 **강제 종료(SIGKILL)** 한다.
`sleep`은 종료 신호를 처리할 줄 모르는 단순한 명령이라 강제 종료됐고, 그 결과가 `137 = 128 + 9`(9번 신호 = SIGKILL).

> 실무에서 중요한 이유: 웹 서버가 강제 종료되면 **처리 중이던 요청이 끊긴다.**
> 그래서 서버는 SIGTERM을 받으면 "새 요청은 안 받고 처리 중인 것만 마저 끝내고 종료"하도록 만든다 → **graceful shutdown**

### 2. `latest`는 "최신"이 아니다

그냥 **기본 태그 이름**일 뿐. 어제의 `latest`와 오늘의 `latest`가 다를 수 있다.
재현 가능한 환경이 목표이므로 실무에선 `ubuntu:24.04`처럼 **버전을 명시**한다.

### 3. `-d`로 띄웠는데 바로 죽는다면

준 명령이 "끝나는 명령"이기 때문이다. PID 1이 끝나면 컨테이너도 끝난다.

### 4. `docker exec`은 실행 중인 컨테이너에만 된다

정지된 것에 하면 `container ... is not running`.
조사하려면 `docker start`로 살리거나, `docker logs`로 마지막 출력을 보거나, `docker cp`로 파일만 꺼낸다.

## 내가 던진 질문들

### Q. 커널이 뭐야?

**운영체제의 심장부.** 하드웨어와 프로그램 사이에서 모든 것을 중재하는 관리자.

```
┌────────────────────────────────────┐
│  프로그램들 (크롬, 파이썬, nginx…)   │
├────────────────────────────────────┤
│           커  널                    │  ← 중재자
├────────────────────────────────────┤
│   하드웨어 (CPU, RAM, 디스크)        │
└────────────────────────────────────┘
```

프로그램은 하드웨어를 **직접 만질 수 없다.** 반드시 커널에게 **시스템 콜**이라는 정해진 양식으로 요청해야 한다. (리눅스와 윈도우는 이 양식이 서로 달라서 못 알아듣는다 → 3단계의 OS 경계)

| 역할 | 하는 일 |
|---|---|
| 프로세스 관리 | 어떤 프로그램에 CPU를 몇 초 줄지 배분 |
| 메모리 관리 | 프로그램별 메모리 구역 배정·회수 |
| 파일 시스템 | 디스크의 0과 1을 "파일" 형태로 보여줌 |
| 장치 제어 | 키보드·화면·랜카드와 대화 |

> **2단계의 권한 검사도 커널이 한 것이다.** `chmod 000` 후 `Permission denied`를 띄운 게 커널.

**커널 ≠ 운영체제 전체**

```
우분투(운영체제) = 리눅스 커널 + 셸(bash) + 명령어들 + 패키지관리자 + …
                   └─ 심장 ─┘   └────────── 나머지 껍데기 ──────────┘
```

리눅스는 사실 **커널의 이름**이고, 우분투·데비안·센토스는 같은 커널에 다른 껍데기를 씌운 "배포판". `Darwin`도 macOS의 커널 이름이라 `uname`이 그렇게 답한다.

**이걸 알면 풀리는 것들**

- **우분투 이미지가 78MB인 이유** — `/boot`가 비어 있고 `/lib/modules`가 아예 없다(직접 확인함). 커널과 드라이버가 빠졌다.
- **1초 만에 뜨는 이유** — 부팅이란 커널을 올리는 과정인데, 컨테이너는 **이미 떠 있는 커널에 프로세스 하나를 추가**할 뿐이라 부팅이 없다.
- **여러 개 띄워도 가벼운 이유** — 컨테이너 100개여도 커널은 하나. VM 100개는 커널도 100개.
- **격리되는 이유** — 커널의 **네임스페이스**(시야 가리기) + **cgroup**(자원 제한). 3단계 `docker info`의 `Cgroup Version: 2`가 이것.

> **결국 컨테이너란 별도의 무언가가 아니라, 커널 기능으로 "가려지고 제한된 그냥 프로세스"다.**

### Q. 커널을 빌려 쓴다는데, 지금 커널은 macOS 커널이잖아. 그래도 상관없어?

**컨테이너는 macOS 커널을 빌려 쓰는 게 아니다.** 실측으로 확인:

| 확인 항목 | 내 맥 | 컨테이너 안 | 해석 |
|---|---|---|---|
| 커널 | `Darwin 24.6.0` | `Linux 6.17.8-orbstack` | **다른 커널** |
| 가동 시간 | 7시간 14분 | 6시간 27분 | **다른 시점에 켜진 다른 기계** |
| 메모리 | 32GB | 15GB | 일부만 떼어 준 별도 공간 |
| 시각 | 17:08 (KST) | 08:08 (UTC) | 시간대도 별개 |

```
❌ 컨테이너는 macOS의 커널을 빌려 쓴다
⭕ 컨테이너는 자기가 속한 리눅스 VM의 커널을 빌려 쓴다
⭕ macOS 커널은 그 VM을 돌려주는 역할까지만 한다
```

3단계에서 그린 "호스트 OS 커널 공유" 그림은 **리눅스 서버 기준**이었다. 맥/윈도우에서는 그 "호스트"가 내 노트북이 아니라 **중간의 리눅스 VM**이다.

**실용적으로는 상관없다.** 컨테이너는 자기가 리눅스 위에 있다는 것만 알면 되고, 진짜 서버인지 맥 안의 VM인지 구분하지 못한다. 그래서 여기서 만든 이미지가 리눅스 서버에서도 똑같이 돈다.

다만 알아둘 것 셋:
1. **메모리를 미리 떼어간다**(32GB 중 15GB) — 안 쓸 때도 VM은 떠 있다
2. **파일 공유가 느리다** — 7단계 바인드 마운트는 VM 경계를 넘어야 해서 리눅스보다 느리다
3. **부팅은 한 번뿐** — VM은 처음 한 번만 부팅, 컨테이너는 여전히 1초

> 배포처(리눅스 서버)에서는 이 VM 층이 통째로 사라진다.
> 개발할 땐 한 겹 손해지만, 실제 서비스가 도는 곳에서는 그 손해가 없다.

### Q. OrbStack이 커널 역할을 하고 호스트 커널을 빌려온 거야?

**방향이 반대.** OrbStack은 커널을 빌려오는 쪽이 아니라 **가져다 놓는** 쪽이다.

```
❌ OrbStack이 macOS 커널을 빌려 → 컨테이너에게 준다
⭕ OrbStack이 리눅스 커널을 통째로 하나 가져와 VM 안에 띄운다 → 컨테이너가 그걸 공유한다
```

핵심은 **층마다 "공유"의 뜻이 다르다**는 것:

| 경계 | 방식 | 넘겨주는 것 | 무게 |
|---|---|---|---|
| macOS ↔ VM | **가상화** | CPU·메모리 같은 **하드웨어 자원** | 무거움(커널이 하나 더 생김) |
| VM ↔ 컨테이너 | **커널 공유** | **커널의 기능**(namespace/cgroup) | 가벼움(프로세스만 늘어남) |

macOS는 VM에게 자기 커널을 빌려주는 게 아니라 **하드웨어를 잘라서 준다.** 그래서 VM은 자기 커널을 따로 가져야 한다.

**"컨테이너는 커널 외의 실행환경만 담아서 가볍다"는 이해는 정확하다.** 직접 확인한 증거:

```
$ docker run --rm ubuntu:24.04 ls -la /boot      → total 0        (커널 자리 텅 빔)
$ docker run --rm ubuntu:24.04 ls /lib/modules   → No such file   (드라이버 없음)
$ docker run --rm ubuntu:24.04 ls /bin | wc -l   → 297            (명령어는 297개)
$ docker run --rm ubuntu:24.04 du -sh /usr       → 77M            (78MB의 대부분)
```

```
운영체제 전체 = [ 커널 + 드라이버 ]  +  [ 명령어 + 라이브러리 + 설정 ]
                └ 컨테이너는 안 가짐 ┘   └── 이미지에 담는 부분(78MB) ──┘
```

### Q. `exec`이 무슨 명령어야?

**exec = execute(실행하다)**. `docker exec`은 "이 컨테이너 안에서 이 명령을 실행해라".

```
docker run  ubuntu:24.04  ls     ← 이미지 이름 → 새 컨테이너가 생김
docker exec  demo         ls     ← 컨테이너 이름 → 기존 컨테이너 안에서 실행
```

**`-it`는 필수가 아니다.** 대화가 필요할 때만 붙인다.

| 상황 | 옵션 |
|---|---|
| `ls`, `cat` 같은 한 방 명령 | 불필요 — 결과만 받고 끝 |
| `bash` 같은 셸을 열어 계속 대화 | `-it` 필요 |

자주 쓰는 옵션: `-w`(작업 디렉토리), `-e`(환경변수), `-u`(다른 계정)

```sh
docker exec -it my-db psql -U postgres        # 컨테이너 안 DB 접속
docker exec my-web nginx -t                   # 설정 문법 검사
docker exec -it my-app bash                   # 문제 생겼을 때 조사
```

> 핵심 쓰임새는 **"돌아가는 서비스를 건드리지 않고 들여다보기"**.
> 재시작하면 원인이 사라지지만, `exec`은 살아있는 상태 그대로 조사할 수 있다.

**같은 단어의 다른 등장**: 3단계의 `exec /bin/sh: exec format error`도 "실행하려는데 형식이 안 맞다"는 뜻. 셸 자체에도 `exec`(현재 프로세스를 새 프로그램으로 교체)이 있고, 5단계 `ENTRYPOINT`에서 PID 1 자리를 정확히 넘겨줄 때 쓰인다.

### Q. PID는 뭐야?

**프로세스 = 실행 중인 프로그램**, **PID = 그 프로세스의 번호표**. (이 맥에서만 597개가 돌고 있음)

```
UID      PID   PPID   CMD
root       1      0   sleep infinity
root       7      0   ps -ef
 ↑         ↑      ↑
누가      번호   부모 번호(나를 실행시킨 프로세스)
```

프로세스는 반드시 다른 프로세스가 낳는다 → 전체가 **가계도(트리)** 를 이룬다.

**PID 1이 특별한 이유**: 부팅 후 커널이 최초로 띄우는, 모든 프로세스의 조상.

| 시스템 | PID 1 |
|---|---|
| macOS | `launchd` |
| 리눅스 서버 | `systemd` |
| **컨테이너** | **내가 `docker run` 뒤에 적은 그 명령** |

커널은 PID 1이 종료되면 그 공간을 정리한다. 이것이 **"컨테이너는 PID 1이 살아있는 동안만 산다"** 의 진짜 이유이고, attach 실험의 설명이다.

**가장 흥미로운 발견 — 같은 프로세스인데 번호가 다르다**

```
$ docker exec demo ps -ef     → PID 1     sleep infinity   (컨테이너 안에서 보면)
$ docker top demo             → PID 2399  sleep infinity   (바깥에서 보면)
```

이것이 **네임스페이스의 실체**다. 커널이 "너에게는 이것만 보이고 번호는 1번부터"라고 시야를 조작한 것.

> 컨테이너는 **자기가 독립된 컴퓨터라고 착각하고 있는 프로세스**다.
> `docker top`이 그 가면을 벗겨 실체를 보여준다.

`docker stop`도 내부적으로는 **PID 1에게 종료 신호를 보내는 것**이고, `Exited (137)`은 그 신호가 SIGKILL(9번)이었다는 기록이다.
